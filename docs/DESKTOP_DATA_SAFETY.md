# Desktop data safety — M1

## Scope and ownership

The canonical Notespace library remains a single SQLite database owned by the Go
server. Tauri only determines its durable application-data path and launches the
sidecar. M1 protects that database during application upgrades; it does not add
an updater, a second application store, automatic deletion of old backups, or
an automatic destructive rollback.

### Invariants

1. A new or older binary must not write to a database with an unknown, altered,
   or non-prefix migration history.
2. If a pre-existing library requires SQL migrations, startup must first produce
   an independent, validated recovery copy.
3. If validation, snapshot creation, or migration fails, startup refuses normal
   operation. The original database and any completed recovery copy are kept.
4. Opening an already-up-to-date database must not create another snapshot.
5. Snapshot filenames are unique. M1 deliberately never prunes backup files;
   retention policy and backup UX are later work.

### Startup and failure graph

```text
SQLite open
  -> Inspect applied migrations and current schema fingerprint
       unknown/newer or inconsistent? -> refuse startup, no migration
  -> pending migrations?
       no  -> standard SQLite startup
       yes, new library -> standard SQLite migration
       yes, existing library
           -> quick_check + integrity_check + foreign_key_check
           -> VACUUM INTO separate .partial.db
           -> full integrity validation of snapshot + sync file
           -> atomically publish unique .db snapshot
           -> migrate existing SQLite database
                success -> full integrity validation -> normal startup
                failure -> refuse; print verified snapshot path
```

`migrations.Inspect` refuses newer unknown migrations and altered recorded
migration checksums before `ensureMetadata` can perform DDL. Migration files
remain append-only and keep their current transactional execution.

The sidecar writes recovery copies next to its database:

```text
<app-data>/notespace.db
<app-data>/notespace.db.recovery/
    pre-migration-<UTC>-<random>.db
```

The snapshot includes committed WAL contents because it is generated by
SQLite, not by copying the main `.db` file while a connection is active.
The copy is independently validated with quick_check, integrity_check, and foreign_key_check before being exposed as a recovery file.
Power-loss durability still depends on operating system and storage behavior.

## Manual recovery after a migration failure

**Do not replace any database file while Notespace or its Go sidecar is running.**

1. Exit Notespace and confirm the `notespace-server` process has stopped.
2. Make a forensic copy of the **entire** application data directory including
   `notespace.db`, `notespace.db-wal`, `notespace.db-shm`, and `.recovery`.
   Do not discard this copy even if the newer app failed to open it.
3. Locate the validated `pre-migration-*.db` path printed in the startup
   error/logs. Choose the snapshot created **before** the attempted upgrade.
4. Move the failed database's `notespace.db` and any associated `-wal` /
   `-shm` files into a separate incident folder. Never mix WAL sidecars from
   the failed database with a recovery snapshot.
5. **Copy**, do not move, that saved snapshot to the canonical
   `notespace.db` path. Keep the saved snapshot untouched in `.recovery`.
6. Open the last known-compatible Notespace build (or a fixed newer build).
   Opening the same broken release may repeat the failure; do not interpret
   that as a failed recovery.
7. Verify representative Notes, Canvas, images, tasks, and activity history
   before removing any incident files.

Do **not** run old binaries against a database that has successfully migrated
to a newer, unknown schema. The compatibility fence will reject this. Restoring
an older snapshot is a deliberate offline recovery operation, not a safe
automatic application-version downgrade.

A desktop startup failure is explicitly sent to the native shell so that the
recovery snapshot location is not mislabeled as a port collision.

If the disk has insufficient free space for a complete snapshot, migration
will not start. Free sufficient space or move the whole library through a
documented offline migration procedure; do not bypass the snapshot check.

## Verification

```sh
cd apps/server
go test ./migrations ./internal/sqlite
go test -race ./...
```

Specific tests cover:
- fresh/current database: no snapshots;
- existing pre-migration data: retained in recovery and upgraded database;
- real SQL migration failure: original and independently readable snapshot;
- unknown future migration: refuse without creating schema metadata;
- modified migration checksums and gaps in migration history.

M2 will add full previous-release installer upgrade and crash-injection tests
on the supported desktop operating systems. A Go integration test is not
a substitute for exercising a real Windows MSI upgrade.
